# 연구 나침반(가칭) 구현 계획서

## 배경

Claude Code로 연구개발을 하다 보면 세 가지 문제가 생깁니다. 세부 문제를 풀다가 원래 연구 질문을 놓치고, 이전에 어떤 방식을 왜 포기했는지 잊고, 코드 구조를 모르는 채 다음 변경을 요청하게 됩니다. 이 계획은 이런 문제를 줄이는 로컬 우선 오픈소스 웹앱을 설계합니다. 연구 질문, 문제 트리, 실험, 결정, 기준선, 자료를 한 흐름으로 기록합니다. 그리고 그 상태를 Claude Code 새 세션과 Archify 구조도로 넘겨줍니다. 첫 버전의 목표는 연구 흐름 하나를 처음부터 끝까지 완주하는 것입니다. 외부 LLM API 키 없이 동작해야 합니다.

- 가칭: 앱 이름은 **연구 나침반(ResearchCompass)**, 패키지와 CLI 이름은 `rcompass`로 둡니다.
- 진행 방식: 이번 단계에서는 계획만 작성합니다. 코드 작성, 패키지 설치, 배포는 다음 세션에서 합니다.
- **사용자 답변 반영 (2026-11-19)**
  - 연구 언어는 Python입니다. 기술 구성은 그대로 둡니다.
  - 실험 하나에 여러 실행(시드, 반복)이 **종종 있습니다**. 그래서 실험 아래에 **Run(실행)**을 두고, 판정은 여러 실행의 집계값으로 합니다(4절).
  - 연구 저장소는 원격과 연결되어 있습니다. 그래서 Archify 코드 근거 연결(`sources`)을 기본 경로로 씁니다(5절).
  - DVC나 Hugging Face는 쓰지 않습니다. 그래서 외부 참조는 로컬 경로(NAS 포함)와 URL, sha256만 지원합니다.
  - 개발에 필요한 스킬은 적극적으로 사용합니다(5절 "개발에 사용할 스킬").

## 1. 저장소에서 확인한 사실과 설계에 사용한 가정

### 확인한 사실 (2026-11-19 기준)

| 항목 | 내용 |
|---|---|
| 작업 저장소 | 작업 폴더는 비어 있고 Git 저장소도 아닙니다. 그래서 **신규 프로젝트**로 진행합니다. 따라야 할 기존 구조나 재사용할 코드는 없습니다. |
| 로컬 도구 | Windows 11, Node v24.15.0, Python 3.10.10, Git(mingw64)이 있습니다. |
| 지정된 Archify 도구 | 저장소에도 없고 `~/.claude/skills`, `~/.claude/plugins`에서도 `archify`를 찾지 못했습니다. 그래서 기본 후보 `github.com/tt-a1i/archify`를 사용합니다. |
| Archify 정체 (README로 확인) | 코딩 에이전트용 **에이전트 스킬**이고 Claude Code를 지원합니다. 아이디어, 계획, 코드베이스를 **자체 완결형 HTML** 인터랙티브 다이어그램으로 만듭니다. 라이선스는 Apache-2.0입니다. |
| 설치 (README로 확인) | 에이전트에게 `https://raw.githubusercontent.com/tt-a1i/archify/main/llms.txt`를 읽고 설치하라고 요청하면 됩니다. 설치 위치는 `~/.claude/skills/` 또는 `.claude/skills/`입니다. |
| 호출 (README로 확인) | 에이전트에게 자연어로 요청합니다(예: "Use Archify to diagram …"). Archify 저장소 안에서는 CLI도 쓸 수 있습니다: `node bin/archify.mjs doctor`, `validate`, `preview`, `deliver`, `compare architecture base.json head.json out.html --json`. 앱이 호출할 수 있는 HTTP API는 **문서에 없습니다**. |
| 입력과 모드 (README로 확인) | 모드마다 스키마가 있는 Typed JSON IR을 씁니다. 모드는 Architecture, Workflow, Sequence, Data Flow, Lifecycle, ERD, Class, Tree, Timeline, Waterfall입니다. Mermaid는 지원 범위가 아닙니다. |
| 코드 근거 (schema 문서로 확인) | `meta.repository`에 저장소 URL과 **전체 커밋 SHA**를 넣습니다. 노드마다 `sources`를 1~3개 달 수 있고, 각 source는 저장소 기준 상대 경로와 선택적 줄 범위를 가집니다. **로컬 Git origin이 일치해야 하고, Git으로 커밋, blob, 줄을 검증합니다.** `provider`는 github, gitee, gitlab입니다. 렌더러에는 `--repo-root`가 필요합니다. |
| 한국어 (README로 확인) | `meta.locale: "ko"`가 내장되어 있습니다. 단, 바뀌는 것은 **UI 문구뿐이고 작성한 내용은 번역하지 않습니다.** |
| 확인하지 못한 것 → **0b단계에서 확인 완료** | 노드 필드 목록을 확인했고, 노드 설명 필드는 **없습니다**. `meta.repository.link_mode`에는 `local-only` 선택지도 있습니다. 상세 내용은 [docs/architecture/README.md](architecture/README.md)의 "Archify 확인 기록"에 있습니다. |

### 설계 가정

1. 사용자는 한 대의 PC에서 혼자 씁니다. 서버는 `127.0.0.1`에만 바인딩하고 인증은 넣지 않습니다.
2. (확정) 연구 코드는 Python입니다. 앱도 Python으로 만들어 빌드 단계 없이 실행되게 합니다.
3. (확정) 실험 하나에 실행이 1개 이상입니다. 실행이 하나뿐이면 화면에서 실행 표를 숨겨 단일 실행처럼 보이게 합니다. 기본 집계는 평균이고, 기준마다 중앙값이나 최악값으로 바꿀 수 있습니다. 통계 검정은 MVP에 넣지 않고, 범위가 겹치면 경고만 합니다.
4. 수치 비교는 "낮을수록 좋음"과 "높을수록 좋음" 두 방향에 목표값 하나로 충분합니다.
5. (확정) 대용량 데이터는 로컬 디스크나 NAS에 있고, 일부는 URL로 접근합니다. 앱은 그 위치와 지문(sha256)만 기록합니다.
6. 앱은 연구 저장소의 Git이나 원본 파일을 **읽지도 쓰지도 않습니다**. 커밋 SHA는 사람이 넣거나 붙여넣는 텍스트로만 다룹니다.
7. Archify 다이어그램 생성은 앱 밖에서 Claude Code와 Archify 스킬로 합니다. 앱은 결과 HTML을 등록하고, 메타데이터를 붙이고, 열람하게 합니다.

## 2. MVP 범위와 이후로 미룰 기능

### MVP(v0.1): 연구 흐름 하나를 완주

| 기능 | 넣는 이유 |
|---|---|
| 프로젝트(연구 질문, 성공 기준, 기준선 0) | 여정 1. 모든 화면이 기대는 기준점입니다. |
| 문제 트리(상위 연결, 이유 한 줄, 상태 "지금 조사"와 "나중에 검토") | 여정 2. "원래 질문을 놓침" 문제를 직접 겨냥합니다. |
| 실험(가설과 판정 기준을 먼저 쓰고, 입력, 설정, 코드 버전, 결과 수치, 파일 연결) | 여정 3. 재현성의 핵심입니다. |
| 실행(Run): 실험당 여러 실행, 실행별 수치, 평균±표준편차와 n 집계, 실행 제외(이유 필수) | 사용자 답변 2. 여러 실행이 종종 있어서 실행이 하나뿐인 모델로는 판정을 왜곡합니다. |
| 결정(채택, 기각, 보류, **채택 철회**)과 기준선 이력 | 여정 4. "왜 포기했는지 잊음" 문제를 직접 겨냥합니다. |
| 프로젝트 홈(질문, 기준별 최신 근거, 집중 문제, 마지막 결정, 다음 행동, 두 가지 진행도) | 여정 5. 며칠 뒤 복귀하는 상황을 위한 화면입니다. |
| 자료 열람과 계보 보기(그래프에서 실험, 데이터 버전, 코드까지) | 재현성 확인용입니다. |
| 작은 첨부 파일 저장과 대용량 외부 참조 | 자료 요구사항입니다. |
| Claude Code 인계 Markdown 내보내기와 결과 블록 붙여넣기 | 세션 단절 문제를 해결합니다. |
| 백업과 복구(zip), 예제 프로젝트, 업데이트 전 자동 백업 | 오픈소스로 독립 사용하려면 필수입니다. |
| 구조도 등록(Archify HTML, 근거 구분, 커밋, 한국어 설명) | "코드 구조를 모른 채 변경 요청" 문제를 겨냥합니다. 생성은 앱 밖에서 하므로 구현 비용이 낮습니다. |
| 보류 아이디어의 "재개 조건" 텍스트 필드 | 입력란 하나라 비용이 거의 없습니다. 조건 자동 평가는 이후로 미룹니다. |

## 3. 대표 사용자 여정과 화면별 핵심 동작

### 공통 요소: 컨텍스트 바 (모든 화면 상단 고정)

~~~
[원래 질문] 동일 평가 100문항 오답을 18→12개 이하로 줄일 수 있는가?
원래 질문 › P2 장문 지문 오답 › E2 문단 요약 후 답변
↩ 돌아갈 곳: 상위 문제 P2 · 현재 기준선 B0(오답 18)
~~~

문제가 깊어져도 원래 질문, 현재 위치, 돌아갈 위치가 한 줄씩 항상 보입니다. "돌아갈 곳"은 상위 문제와 현재 기준선을 가리킵니다.

### 입력 부담: 지금 꼭 쓸 것과 나중에 채울 것

| 시점 | 필수(빠른 입력) | 나중에 채워도 됨 |
|---|---|---|
| 프로젝트 생성 | 제목, 연구 질문, 성공 기준 1개 이상(이름, 방향, 목표값), 기준선 0의 이름 | 기준선 0의 실행별 수치(기준선 측정 실험 E0에 기록. 비어 있으면 "미측정"), 기준별 집계 방식과 `min_runs`(기본값: 평균, 1), 배경 메모 |
| 하위 문제 추가 | 제목, **이 문제를 푸는 이유 한 줄**, 상태(기본값 "지금 조사"). 상위 문제는 현재 위치로 자동 지정 | 상세 설명, 재개 조건("나중에 검토"일 때) |
| 실험 생성 | 제목, **가설**, **판정 기준**. 출발 기준선은 현재 기준선으로 자동 지정되고, 실행 R1이 자동으로 만들어짐 | 설정, 데이터 버전, 코드 버전(실험 공통값) |
| 실험 중 | 없음(메모만 선택) | 전부 |
| 실행 추가 | 라벨 하나(예: `seed=2`). 공통 설정, 데이터, 코드는 실험에서 상속 | 실행별 설정 차이, 실행별 코드 커밋 |
| 결과 기록 | 실행마다 수치 1개 이상 또는 결과 메모. 여러 실행은 표에 한 번에 붙여넣기(행은 실행, 열은 지표) | 그래프와 표 파일, 로그 |
| 결정 | 결정 종류, **이유 한 줄** | 상세 분석 |
| **채택 시 재현성 관문** | 채택 전까지 데이터 버전, 코드 커밋 또는 버전 메모, 설정이 있어야 하고, 기준별 **최소 실행 수**(`min_runs`)도 채워야 합니다. 하나라도 없으면 채택 버튼 대신 "빠진 항목 채우기"가 나옵니다. | 기각과 보류는 경고만 하고 그대로 저장합니다. |

### 화면 1: 프로젝트 홈 (여정 1, 5)

- **원래 질문** 카드.
- **성공 기준 표**: 기준, 목표, 현재 기준선 값(예: `11.0 ± 1.0 (n=3)`), 최근 시도 값(실험 ID와 결정), 상태(`달성`, `미달`, `근거 부족`, `미측정`). 미측정 기준은 회색 배지와 "측정 실험 만들기" 버튼으로 드러냅니다. 근거 부족 기준은 "실행 2/3" 힌트를 보여줍니다.
- **두 진행도를 분리해서 표시**합니다.
  - 목표 달성: "성공 기준 2개 중 달성 1, 미달 0, 미측정 1"
  - 작업 진행: "실험 완료 2/3, 문제 해결 1/4"
  - 안내 문구 "작업 진행은 목표 달성을 뜻하지 않습니다"를 붙입니다.
- **지금 집중할 문제**: 경로가 함께 보이고, 사용자가 핀으로 지정합니다.
- **마지막 결정**: 종류, 이유, 날짜.
- **다음 행동**: 한 줄이고 바로 고칠 수 있습니다.
- 버튼: `새 하위 문제`, `새 실험`, `Claude Code 인계 복사`, `백업`.

### 화면 2: 문제 트리 (여정 2)

- 루트는 연구 질문입니다. 각 노드에는 제목, 이유 한 줄, 상태 칩(지금 조사, 나중에 검토, 해결, 중단), 실험 결과 아이콘(✔ 채택, ✘ 기각, ⏸ 보류)이 붙습니다.
- 인라인 `+ 하위 문제`는 제목과 이유 두 칸만 받습니다.
- "나중에 검토" 노드는 트리 아래의 **보류 서랍**에 모입니다. 재개 조건이 함께 보이고, `지금 조사로 전환` 버튼이 있습니다.
- 노드를 선택하면 오른쪽 패널에 해당 실험 목록과 `여기서 다음 시도` 버튼이 나옵니다.

### 화면 3: 실험 상세 (여정 3, 4)

위에서 아래 순서로 배치합니다.

1. **가설과 판정 기준**: 생성 시 고정됩니다. 수정하면 이력이 남고, 결과를 기록한 뒤 고치면 경고합니다.
2. **입력**: 데이터 버전 선택, 코드 커밋 SHA 또는 버전 메모, 설정(텍스트 붙여넣기 또는 파일 첨부), 출발 기준선(자동).
3. **실행과 결과**: 실행 표(행은 R1, R2, …, 열은 지표)와 그 아래 집계 행(평균 ± 표준편차, 최소~최대, n)을 보여줍니다. 실행이 하나면 표 대신 수치 목록만 보입니다. 실행은 `제외`할 수 있습니다. 이유가 필수이고, 삭제하지 않고 집계에서만 뺍니다. 각 지표는 성공 기준과 연결할 수 있습니다. 그래프와 표 파일은 실험 또는 특정 실행에 첨부하고, `Claude Code 결과 붙여넣기`도 여기서 합니다.
4. **판정 패널**: 판정 기준과 기준선 대비 차이를 나란히 보여줍니다(예: "18.0 ± 1.0 (n=3) → 19.0 ± 1.0 (n=3), +1.0"). 실행별 점도 함께 그립니다. 두 범위가 겹치면 "차이가 실행 간 변동 안에 있습니다" 경고를 보여줍니다. 버튼은 `채택`, `기각`, `보류`입니다. 채택된 실험에는 `채택 철회`가 나옵니다.
5. **결정 이력**: 시간순이고 덮어쓰지 않습니다.
6. 기각한 뒤에는 `상위 문제 P2에서 다음 시도`와 `기준선 B0에서 다음 시도` 버튼을 보여줍니다.

### 화면 4: 자료 열람

- 탭은 `데이터셋`, `파일`, `구조도`입니다.
- 데이터셋 버전 상세: 출처, 수집일, 버전 라벨, 저장 방식(첨부 또는 외부 참조), 지문(sha256), 이 버전을 쓴 실험 목록.
- 파일 상세: 미리보기(이미지, CSV 표, 텍스트)와 **계보 체인**(아래 4절 예시).
- 구조도: sandbox iframe으로 열람합니다. "계획 단계 예상 구조"와 "코드 근거" 배지, 커밋, 관련 파일, 한국어 설명을 함께 보여줍니다.

## 4. 데이터 모델과 관계, 결정에 따른 상태 변화

### 엔터티 (SQLite 하나에 저장)

ID는 프로젝트 안에서 사람이 읽을 수 있는 짧은 번호(P3, E7, B2, D5, F4, DS1)이고, 내부 PK는 별도로 둡니다. 인계 문서와 결과 블록에서 이 짧은 ID로 참조합니다. 번호는 1부터 발급하고, E0(기준선 측정 실험)과 B0은 프로젝트를 만들 때만 붙이는 예약 번호입니다.

1단계 구현에서 정한 세부 사항은 다음과 같습니다.
- 실행 제외는 `RunExclusion` 행으로 기록합니다(추가만 가능, 실행당 하나).
- 기준선 스냅샷은 `BaselineRun`(기준선, 실행, 추가한 BaselineChange)으로 기록합니다.
- 기준선 변경 종류는 `initial`, `adopt`, `revoke`, `snapshot_update` 네 가지입니다.
- 결과 기록 뒤 가설과 판정 기준을 고친 이력은 `ExperimentRevision`에 남깁니다.

4단계 구현에서 정한 사항은 다음과 같습니다.
- 실험을 만들 때 실행 R1을 자동으로 만들지 않습니다. 결과는 "실행 × 지표" 표를 붙여넣어 기록하고, 실행은 표의 행에서 생깁니다. 실행이 하나여도 같은 방식입니다.
- 실험 안에서 실행 이름은 고유합니다(마이그레이션 0002). 같은 이름으로 다시 붙여넣으면 그 실행의 값을 고칩니다.
- 기준선 근거인 실행의 값은 바꿀 수 없습니다. 바꾸려면 새 실행 이름으로 기록합니다.
- 가설과 판정 기준은 결과가 생긴 뒤에도 고칠 수 있지만, 확인란에 체크해야 하고 변경 이력이 남습니다.
- 데이터 버전 등록은 먼저 외부 참조(경로나 URL)만 지원합니다. 첨부 파일과 지문 계산은 5단계에서 추가합니다.

5단계 구현에서 정한 사항은 다음과 같습니다.
- 같은 내용을 다시 첨부하면 디스크에는 한 번만 저장되고, 파일 기록(F#)은 새로 생깁니다. 실행, 종류, 설명이 다를 수 있기 때문입니다.
- 실험에 첨부한 파일은 그 시점의 실험 입력 데이터 버전을 출처(`file_derivations`)로 함께 기록합니다.
- 지문 계산은 로컬·NAS 절대 경로와 `file://` URI만 대상으로 합니다. URL과 상대 경로는 계산하지 않습니다. 기록한 지문과 다르면 기록은 그대로 두고 "불일치"만 알립니다.
- 브라우저에서 바로 보여주는 형식은 래스터 이미지와 텍스트뿐입니다. SVG, HTML 등은 내려받기로만 제공합니다(Archify 구조도 열람은 10단계의 sandbox iframe에서 다룹니다).

6단계 구현에서 정한 사항은 다음과 같습니다.
- 보류한 실험은 다시 판정(채택이나 기각)할 수 있습니다. 기각과 철회는 마지막 판단이라, 다시 시도하려면 새 실험을 만듭니다.
- 재현성 관문의 `min_runs`는 이 실험이 잰 기준에만 적용합니다. 성공 기준 지표를 하나도 재지 않았으면 채택할 수 없습니다. 현재 기준선에서는 쟀지만 이 실험에서 재지 않은 기준은 "새 기준선에서는 미측정이 됩니다"라고 경고만 합니다.
- 설정은 텍스트로 적었거나 이 실험에 설정 파일(종류: 설정)을 첨부했으면 채운 것으로 봅니다.
- 판정 패널은 출발 기준선과 비교합니다. 출발 기준선의 채택이 철회되었으면 현재 기준선과 비교하고 그 사실을 알립니다.
- 범위 겹침 경고는 두 쪽 중 하나라도 실행이 2개 이상일 때만 띄웁니다.
- 판정한 실험(보류 제외)은 가설과 판정 기준을, 채택했던 실험은 입력(데이터, 코드, 설정)을 고칠 수 없습니다. 기각한 실험의 입력은 나중에 채울 수 있습니다.
- 철회하는 기준선 위에 다른 기준선이 있어 복귀 대상을 고를 때는 "현재 기준선 유지"도 고를 수 있습니다. 이때도 철회 기록(BaselineChange)은 남습니다.

7단계 구현에서 정한 사항은 다음과 같습니다.
- 작업 진행의 "실험 완료"는 채택·기각·철회로 판정을 마친 시도 실험입니다. 보류는 따로 세고, 결과가 있지만 판정하지 않은 실험은 "판정 대기"로 링크합니다. 문제 해결 수는 중단한 문제를 빼고 셉니다.
- 성공 기준 표의 "최근 시도"는 그 지표를 마지막으로 기록한 시도 실험(E0 제외, 제외한 실행 빼고)의 값과 판정 상태입니다. 채택하기 전에는 목표 달성에 반영되지 않는다고 안내합니다.
- 미측정 기준의 버튼은 현재 기준선이 B0이면 E0에 측정값을 기록하는 곳으로, 그 밖에는 집중 문제(없으면 문제 트리)에서 측정 실험을 만드는 곳으로 갑니다. 현재 기준선이 B0이 아니면 측정 실험을 채택해야 그 기준이 채워집니다.
- 다음 행동은 홈에서 바로 고치는 한 줄(300자 이내)입니다.
- 홈에 기준선 이력(최근 6건)을 함께 보여줍니다. Claude Code 인계와 백업 버튼은 8단계와 9단계에서 추가합니다.

8단계 구현에서 정한 사항은 다음과 같습니다.
- **기준선 측정 실험(사용자 결정, 2026-11-24)**: 현재 기준선에서 재지 않은 지표(예: 응답 시간)는 "기준선 측정 실험"으로 채웁니다. E0이 B0에 하듯이, 기록한 실행이 그 기준선의 근거에 더해집니다(BaselineChange `snapshot_update`).
  - 측정 실험은 만들 때의 현재 기준선을 잽니다. 그 기준선이 여전히 현재 기준선일 때만 근거에 더해집니다.
  - 가설과 판정이 없습니다.
  - E0 밖의 측정 실험은 그 기준선이 아직 재지 않은 지표만 기록할 수 있습니다. 채택한 기준선이 이미 가진 수치는 바뀌지 않습니다.
  - 7절 시나리오 7번의 E3이 이런 측정 실험입니다.
- 인계 문서의 "결과 보고 형식"에는 대상 실험을 고릅니다. 집중 문제에서 아직 결과가 없는 실험이 우선이고, 없으면 프로젝트의 가장 최근 결과 없는 실험입니다. 측정 실험이면 기준선 근거 실험의 데이터·코드·설정을 채우고, 아직 재지 않은 지표만 적습니다.
- 결과 블록은 Claude Code 출력 전체를 붙여넣어도 ```` ```rcompass-result ```` 펜스 안만 읽습니다. 값을 비운 지표와 `<...>` 안내 문구는 빈 값으로 봅니다.
- 블록의 `note`는 미리보기에서만 보여주고 기록하지 않습니다. `files`는 첨부 제안으로만 보여줍니다.
- 블록의 코드·설정이 실험 값과 다르면 이번에 기록한 실행의 코드·설정(Run override)으로 남깁니다. 실험 값이 비어 있으면 실험 값으로 채웁니다(채택했던 실험 제외).
- 명령줄: `rcompass handoff [프로젝트 번호] [-e 실험] [-o 파일]`. DB는 읽기만 합니다.
- 연구 저장소용 스킬은 `integrations/claude-code/rcompass-result/SKILL.md`, 설명과 CLAUDE.md 두 줄 스니펫은 `integrations/claude-code/README.md`에 있습니다.

### 결정에 따른 상태 변화 (하나의 트랜잭션으로 처리)

| 동작 | 생성되는 레코드 | 실험 outcome | 현재 기준선 | 성공 기준 표시 |
|---|---|---|---|---|
| **채택** | Decision(adopt). 새 Baseline B(n+1)을 만들고 parent는 이전 기준선, source는 이 실험, run_ids는 지금 포함된 실행. BaselineChange(Bn → Bn+1) | adopted | B(n+1) | 새 기준선 수치로 다시 계산 |
| **기각** | Decision(reject, 이유 필수) | rejected | 변화 없음 | 최근 시도 값만 갱신하고 기준선 값은 유지 |
| **보류** | Decision(hold, 재개 조건 선택) | held | 변화 없음 | 같음 |
| **채택 철회** | Decision(revoke, revokes=원래 adopt, 이유 필수). BaselineChange(Bn+1 → 복귀 대상). 기본 복귀 대상은 철회되는 기준선의 parent | revoked. 이전 adopt 결정도 그대로 남음 | parent 기준선(또는 사용자가 고른 기준선) | 복귀한 기준선으로 다시 계산하고, 이력에 "철회됨"으로 표시 |

규칙은 다음과 같습니다.

- 결정은 지우지 않습니다. 실험 화면에서 "채택(11/18) → 철회(11/20, 평가셋 누수 발견)"처럼 예전 판단과 새 판단을 모두 볼 수 있습니다.
- 철회하는 기준선 위에서 이미 다른 기준선이 채택되었다면 막지 않습니다. 대신 "B3이 B2 위에 있습니다" 경고를 띄우고 복귀 대상을 명시적으로 고르게 합니다.
- 기준선 변경은 DB 레코드만 바꿉니다. Git, 원본 데이터, 연구 저장소 파일은 건드리지 않고 화면에 "앱 기록만 바뀝니다"라고 안내합니다.
- 성공 기준 상태는 이렇게 정합니다. 집계에는 현재 기준선의 스냅샷 실행(`run_ids`)만 씁니다. 표준편차는 표본 표준편차(n−1)입니다.
  - 해당 metric 값이 하나도 없으면 `미측정`
  - 실행 수가 `min_runs`보다 적으면 `근거 부족`
  - 집계값(`aggregate`)이 목표를 만족하면 `달성`
  - 그 밖에는 `미달`
- 실행 제외도 덮어쓰지 않습니다. 제외 시각과 이유가 남습니다. 채택 전에는 집계에서 바로 빠집니다. 채택 뒤 스냅샷에 든 실행을 제외하면 기준선 수치는 그대로 둡니다. 대신 홈과 결정 이력에 "기준선 근거 실행 R2가 제외됨, 철회 또는 재판정을 검토하세요" 경고를 띄웁니다.

### 자료와 재현성

- **작은 첨부 파일**(기본 50MB 이하, 설정 가능): 데이터 디렉터리의 `files/sha256/ab/abcdef…`에 내용 주소 방식으로 복사합니다. 같은 파일은 중복 저장하지 않으며, 백업에 포함됩니다.
- **대용량 외부 데이터 참조**: 위치(로컬 또는 NAS 경로, `https://` URL), 크기, 선택적 sha256, 마지막 확인 시각만 기록합니다. DVC나 Hugging Face 전용 식별자는 지원하지 않습니다(사용자 답변 4). 로컬 경로일 때는 `지문 계산` 버튼으로 sha256을 기록합니다. 백업에는 **포함하지 않고**, 백업 manifest에 "외부 참조 목록(별도 보관 필요)"으로 남깁니다. 복구 후에는 각 참조를 "접근 가능", "없음", "지문 불일치"로 보고합니다.
- **역추적 예시**(그래프에서 원본 실험까지):

~~~
F4 오답유형_E2.png (첨부, sha256 9c1e…)
 └ 생성 실행: E2/R1 (seed=1)
    └ 실험: E2 문단 요약 후 답변 (문제 P2 장문 지문 오답, 이유: "오답 18 중 7이 장문")
       ├ 가설: 지문을 문단별 요약 후 답하면 장문 오답이 줄어든다
       ├ 판정 기준: 평균 오답 ≤ 17이고 다른 유형 악화 없음 → 채택 (n ≥ 3)
       ├ 입력 데이터: DS1 eval-100 v1.0 (출처: 내부 QA 수집, 수집일 2026-11-02, 외부 참조 D:/data/eval100_v1.jsonl, sha256 41ab…)
       ├ 코드: a1b2c3d (연구 저장소 qa-bot) · 설정: configs/summarize.yaml (첨부 F3)
       ├ 결과: wrong_count R1 11 · R2 12 · R3 10 → 11.0 ± 1.0 (n=3)
       └ 결정: D2 채택 (2026-11-18) → 기준선 B1 "문단 요약 v1"
~~~

## 5. 권장 기술 구성, 저장 방식, Archify와 Claude Code 사용 흐름

### 기본안 (하나만 추천)

**Python 3.10+, FastAPI, Jinja2 서버 렌더링, htmx(정적 파일로 동봉), SQLAlchemy 2, Alembic, SQLite(WAL), Typer CLI, pytest. 설치는 `uv`로 하고 `pip`도 대체 경로로 지원합니다.**

이 조합을 고른 이유는 다음과 같습니다.

- 연구자 대부분에게 이미 Python이 있습니다.
- JS 빌드 단계가 없어 클론한 뒤 바로 실행됩니다.
- 하나의 프로세스, 하나의 DB 파일, 하나의 파일 폴더로 동작하므로 백업이 단순합니다.
- CLI와 웹이 같은 서비스 계층을 공유하므로 Claude Code가 CLI로 인계 문서를 만들기 쉽습니다.
- 그래프는 사용자가 만든 이미지를 첨부합니다. 기준별 추이 같은 작은 차트는 서버에서 인라인 SVG로 만들어 외부 JS 의존성을 없앱니다.
- htmx와 CSS는 저장소에 동봉해 오프라인에서도 동작합니다.

### 저장 위치와 비밀값

| 항목 | 위치 |
|---|---|
| 코드 | 클론한 저장소. 개인 데이터는 커밋하지 않습니다. |
| 데이터 디렉터리 | 기본값은 `platformdirs`의 사용자 데이터 경로입니다(Windows는 `%LOCALAPPDATA%\rcompass`, macOS와 Linux는 `~/.local/share/rcompass`). `RCOMPASS_DATA_DIR` 환경변수나 `--data-dir` 옵션으로 바꿀 수 있습니다. |
| 데이터 디렉터리 내용 | `rcompass.db`, `files/`, `backups/`, `config.toml`(첨부 크기 한도, 포트) |
| 비밀값 | MVP에는 비밀값이 없습니다. 이후 선택형 LLM 키는 환경변수나 데이터 디렉터리의 `.env`에만 두고, DB, 백업, 인계 문서에는 절대 넣지 않습니다. 백업 생성 시 `.env`는 제외합니다. |
| 저장소 `.gitignore` | `.env`, `data/`, `*.db`, `backups/` |

### Claude Code 사용 흐름

1. **인계**: 홈에서 `Claude Code 인계 복사`를 누르거나 `rcompass handoff P1`을 실행해 Markdown을 만듭니다. 새 Claude Code 세션 첫 메시지에 붙여넣습니다. 분량은 60줄 안팎이 목표입니다. 기각된 접근은 현재 집중 문제의 경로와 연구 질문 바로 아래 문제에 속한 것을 모두 넣고, 나머지는 개수만 적습니다.
2. **결과 회수**(가장 간단한 방식): 인계 문서 끝에 결과 블록 형식이 들어 있습니다. Claude Code는 실험이 끝나면 그 블록을 출력합니다. 연구자는 실험 상세에서 `결과 붙여넣기`로 블록을 붙여넣습니다. 앱은 YAML을 파싱해 **미리보기(초안)**로 보여주고, 연구자가 값을 고친 뒤 `확인하고 기록`을 눌러야 저장됩니다(provenance=claude_confirmed). 파일 경로는 첨부 제안으로만 표시하고, 연구자가 실제로 파일을 올려야 연결됩니다.
3. 연구 저장소의 `CLAUDE.md`에 넣을 2줄짜리 스니펫을 README에 제공합니다. "실험을 마치면 `rcompass-result` 블록으로 보고하라", "인계 문서의 기각된 접근은 이유가 해소되지 않으면 재제안하지 말라"입니다.

**인계 출력 예시** (새 세션에 그대로 붙여넣는 형태):

~~~markdown

### Archify 사용 흐름 (확인된 기능만 사용)

앱은 Archify를 직접 호출하지 않습니다. 연구자나 유지보수자가 Claude Code에 설치된 Archify 스킬로 HTML(필요하면 JSON IR도)을 만들고, 앱의 `구조도 등록`으로 올립니다.

| 구조도 | 누가 | 언제 만들고 갱신하나 | 근거 구분 | 앱에서 연결 |
|---|---|---|---|---|
| **연구 절차도** (Workflow 모드) | 연구자. 앱이 `다이어그램 요청문 내보내기`로 문제 트리, 실험, 결정을 텍스트로 만들어 주면 Claude Code에 "Archify로 workflow 다이어그램을 만들어 줘"라고 요청합니다. | 채택이나 철회로 기준선이 바뀔 때, 주간 회고 때 | "연구 기록 스냅샷 (날짜)" | 프로젝트, 기준선 |
| **웹앱 코드 구조도** (Architecture 모드) | 이 저장소 유지보수자(Claude Code와 Archify) | 지금은 "계획 단계 예상 구조"만 만듭니다(코드가 없으므로). 구현 단계가 끝날 때마다 코드 근거 구조도로 다시 만듭니다. | 처음에는 `planned`, 이후 `code_backed`(`meta.repository` 커밋 SHA와 노드별 `sources`) | 저장소 `docs/architecture/`에 `*.json`, `*.html`, `README.md`(한국어 설명) |
| **연구 저장소 코드·데이터 흐름도** (Architecture, Data Flow 모드) | 연구자가 자기 연구 저장소에서 Claude Code와 Archify로 만듭니다. | 큰 변경을 요청하기 **전**, 새 기준선을 채택할 때 | 코드를 읽고 만들면 `code_backed`, 변경 구상은 `planned` | 실험, 기준선. 기준선 커밋 ≠ 구조도 커밋이면 "구조도가 기준선보다 오래됨" 배지 |

- **한국어 설명**: `meta.locale: "ko"`는 UI만 번역하므로, 쉬운 한국어 설명(3~6문장, "이 그림에서 볼 것")은 앱의 `Diagram.explanation_ko`에 따로 저장하고 그림 옆에 보여줍니다. 웹앱 구조도는 `docs/architecture/README.md`에 같은 설명을 둡니다.
- **코드 근거 연결**: code_backed 구조도는 커밋 SHA(전체)와 관련 파일 경로가 필수입니다. 연구 저장소와 이 저장소 모두 원격이 있으므로(사용자 답변 3) Archify의 `meta.repository`(URL과 전체 SHA)와 노드별 `sources`를 기본으로 씁니다. 앱은 같은 SHA와 경로를 `Diagram`에 저장합니다. 그래서 그림 속 `SRC` 링크와 앱의 기준선 커밋 비교가 같은 근거를 가리킵니다. 고정한 커밋이 원격에 푸시되지 않으면 Git 검증이 실패할 수 있으므로 "구조도는 푸시된 커밋에서 생성"을 규칙으로 둡니다.
- **변경 비교**: 웹앱 구조도는 구현 단계 전후 JSON으로 `compare architecture base.json head.json delta.html`을 만들어 PR에 첨부할 수 있습니다(README에 문서화된 명령).
- **보안**: 등록한 HTML은 `sandbox="allow-scripts"` iframe(same-origin 없이)으로만 엽니다.

### 개발에 사용할 스킬

사용자가 적극 사용을 허용했습니다. 이 저장소를 개발할 때 아래 스킬을 정해진 시점에 씁니다. 모두 현재 세션에서 사용 가능함을 확인했고, Archify만 0단계에서 새로 설치합니다.

| 스킬 | 시점 | 용도 |
|---|---|---|
| **Archify** (프로젝트 로컬 `.claude/skills/archify`에 설치) | 0단계 직후, 6·10·11단계 종료 시 | 0단계: "계획 단계 예상 구조"(`planned`) 웹앱 구조도를 만듭니다. 이후 단계: 푸시된 커밋 기준 코드 근거 구조도와 `compare` 변경 비교를 만듭니다. 설치는 README의 `llms.txt` 안내를 따르고, 설치 직후 `doctor`로 환경을 확인합니다. |
| `init` | 0단계 | 이 저장소의 `CLAUDE.md`를 만듭니다. 계획서 요약, 불변 규칙(결정과 기준선은 추가만 가능, 연구 저장소 Git에 쓰지 않음), 테스트 명령을 담습니다. |
| `run` | 매 단계 완료 시 | 앱을 실제로 띄워 "사용자가 확인할 수 있는 결과" 열을 브라우저로 확인합니다. |
| `code-review` | 매 단계 완료 시 | 변경분의 정확성 버그를 점검합니다. 특히 6단계 결정 전이와 9단계 백업은 반드시 거칩니다. |
| `security-review` | 5, 9, 10단계 | 업로드 경로 탈출, zip 복구 시 경로 조작(zip slip), 업로드 HTML의 iframe 격리, 로컬 바인딩을 점검합니다. |
| `simplify` | 단계가 커졌을 때 | 서비스 계층의 중복을 정리합니다. |
| `dataviz` | 6, 7단계 | 판정 패널의 실행별 점과 범위 표시, 홈의 기준별 추이 인라인 SVG의 색상, 축, 접근성을 정합니다. |

연구자를 위한 배포물에도 스킬을 하나 넣습니다. `integrations/claude-code/rcompass-result/SKILL.md`입니다. 연구자가 자기 연구 저장소의 `.claude/skills/`에 복사하면, Claude Code가 실험을 마칠 때 `rcompass-result` 블록을 출력하고 인계 문서의 기각된 접근을 존중합니다. README의 CLAUDE.md 스니펫과 같은 내용을 스킬 형태로 제공하는 것입니다(8단계).

### 오픈소스 배포

- **실행 경로**:

  ~~~
  git clone …/rcompass && cd rcompass
  uv sync
  uv run rcompass init --example
  uv run rcompass serve
  ~~~

  `init --example`은 데이터 디렉터리를 만들고 예제 프로젝트를 심습니다. `serve`를 실행한 뒤 브라우저에서 `http://127.0.0.1:8765`을 열면 됩니다. 홈의 `새 연구`가 첫 연구 생성 지점입니다. pip 경로는 `python -m venv .venv` 후 `pip install -e .`입니다.
- **라이선스**: **Apache-2.0**을 추천합니다. 특허 조항이 있어 연구 기관 사용에 유리하고, Archify와 같은 라이선스입니다. 대안은 MIT입니다.
- **예제 프로젝트**: 7절 검증 시나리오와 같은 "QA 평가 오답 줄이기"입니다. 작은 CSV, 그래프 PNG 2개, 외부 참조 1건, 기각 1건, 채택 1건, 실험당 실행 3개를 포함합니다.
- **업데이트**: `git pull`, `uv sync`, `rcompass migrate` 순서입니다. migrate는 실행 전에 **자동 백업**을 만들고 Alembic을 적용합니다. `serve`를 시작할 때 스키마가 오래되었으면 안내만 하고 자동으로 마이그레이션하지는 않습니다. SemVer와 CHANGELOG를 사용합니다.
- **백업과 복구**:
  - `rcompass backup` 또는 UI 버튼을 쓰면 `rcompass-backup-YYYYMMDD-HHMM.zip`이 만들어집니다. 내용은 `manifest.json`(앱 버전, 스키마 버전, 레코드 수, 파일별 sha256, 외부 참조 목록), `db.sqlite`(`VACUUM INTO`로 일관된 스냅샷), `files/`입니다.
  - `rcompass restore <zip> [--data-dir]`는 지문을 검증하고, 기존 데이터가 있으면 거부하거나 `--force`일 때 기존 데이터를 먼저 백업합니다. 그다음 필요하면 마이그레이션하고 외부 참조 점검 보고를 출력합니다.

## 7. 검증 시나리오: 오답 18개를 12개 이하로

`tests/scenario/test_wrong_answers.py`가 서비스 계층과 HTTP로 아래 단계를 자동 실행합니다. 같은 데이터가 예제 프로젝트에도 들어가므로 사람도 화면으로 따라갈 수 있습니다.

1. **프로젝트 생성**
   - 질문: "동일 평가 100문항에서 오답을 18→12개 이하로 줄일 수 있는가?"
   - C1: `wrong_count`, 낮을수록 좋음, 목표 ≤ 12, 평가셋 DS1 eval-100 v1.0, 집계 평균, `min_runs` 3
   - C2: `avg_latency_s` ≤ 2.0
   - 기준선 B0 "현행 프롬프트 v1": E0에 실행 3개(17, 18, 19) 기록
   - 확인: 홈에 C1 `미달(18.0 ± 1.0, n=3)`, C2 `미측정`, 목표 달성 0/2(미측정 1)가 보임
2. **문제 분해**
   - P1 "오답 유형 분석"(이유: 개선 방향 결정)
   - P2 "장문 지문 오답"(이유: 18개 중 7개가 장문)
   - P3 "모델 교체"는 `나중에 검토`(재개 조건: 프롬프트 개선이 한계에 도달하면)
   - 확인: P3이 보류 서랍에 있음
3. **기각 경로**: P2 아래 E1 "few-shot 예시 3개"
   - 판정 기준: 평균 ≤ 17이면 채택, 평균 ≥ 18이면 기각
   - 결과: 실행 3개 wrong_count 18, 19, 20 → 19.0 ± 1.0 (n=3), 데이터 DS1 v1.0, 코드 `3f2a…`
   - 확인: 판정 패널에 "18.0 → 19.0 (+1.0)"과 "범위가 겹침" 경고가 함께 보임
   - `기각`, 이유: "평균 오답 +1, 형식 오류 2건 증가"
   - 확인:
     - 현재 기준선은 여전히 B0이고 C1은 `미달(18.0)`, 최근 시도는 "E1 19.0 기각"
     - 작업 진행은 "실험 1/1 완료"인데 목표 달성은 0/2로, 두 진행도가 다르게 보임
     - `P2에서 다음 시도` 버튼이 E2의 출발 기준선을 B0으로 채움
4. **채택 경로**: E2 "문단 요약 후 답변"
   - 먼저 실행 2개(11, 12)만 기록하고 `채택`을 누릅니다. `min_runs` 3을 채우지 못했으므로 재현성 관문이 막고 "실행 2/3"을 보여주는지 확인합니다.
   - 세 번째 실행(10)을 추가합니다. 결과는 11.0 ± 1.0 (n=3)입니다. 그래프 F4 `오답유형_E2.png`를 R1에 첨부하고 설정 F3을 연결합니다.
   - 데이터 버전을 비운 채 `채택`을 누르면 재현성 관문이 막는지 확인
   - 데이터 버전을 채운 뒤 `채택`, 이유: "목표 달성, 다른 유형 악화 없음"
   - 확인: B1이 생기고(parent B0), C1 `달성(11.0 ± 1.0, n=3)`, C2 `미측정`, 마지막 결정 D2 채택
   - 추가 확인(단위 테스트): 채택 뒤 R2를 "로그 손상"으로 제외해도 B1은 스냅샷(R1~R3) 그대로 11.0입니다. 홈과 결정 이력에는 "근거 실행 제외됨" 경고가 뜹니다. 채택 전에 제외했다면 10.5 (n=2), `근거 부족`이 되고 채택이 막힙니다.
5. **채택 철회 추적**
   - "평가셋 일부가 예시에 섞임"을 이유로 D2를 철회
   - 확인:
     - 현재 기준선이 B0으로 돌아가고 C1은 `미달(18)`
     - E2 화면에 "채택 → 철회" 두 결정이 모두 보임
     - B1 레코드는 남아 있음
     - 연구 저장소와 Git에는 변화가 없음(테스트 중 임시 Git 저장소의 HEAD와 파일 해시가 그대로)
   - 이후 누수 예시를 뺀 재검증 실험 E2b(실행 3개, 평균 11.3)를 채택해 B2를 만들고 다음 단계로 넘어갑니다.
6. **데이터와 그래프 역추적**
   - 자료 열람에서 F4를 열고 계보 체인을 확인: 실행 E2/R1, 실험 E2, DS1 v1.0(출처, 수집일, sha256), 코드 SHA, 설정 F3, 결정(채택과 철회), 기준선 B1
   - 체인의 각 링크를 눌러 해당 화면으로 이동
7. **새 Claude Code 세션으로 인계**
   - 홈에서 `인계 복사` 후 새 세션에 붙여넣기
   - 확인 질문 세 가지:
     - "현재 기준선과 그 수치는?" → B2, 11.3 (n=3)
     - "E1 방식을 다시 시도할까?" → 기각 이유를 들어 재제안하지 않음
     - "다음 행동은?" → 응답 시간 측정
   - 홈의 "측정 실험 만들기"로 현재 기준선 B2의 기준선 측정 실험 E3을 만들고, Claude Code가 실행 3개짜리 E3 결과 블록을 출력하면 붙여넣고 미리보기에서 값을 수정한 뒤 확인. 실행 3개가 Run으로 나뉘어 `provenance=claude_confirmed`로 기록되고, C2가 `미측정`에서 `달성` 또는 `미달`로 바뀜
8. **새 환경에서 백업 복구**
   - `rcompass backup` 실행
   - 다른 폴더에 새로 클론하고 `RCOMPASS_DATA_DIR=<새 경로>`로 `rcompass restore <zip>` 실행
   - 확인:
     - 레코드 수와 파일 sha256이 manifest와 일치
     - F4 미리보기가 정상
     - 외부 참조 DS1은 "접근 가능" 또는 "없음"으로 보고됨
     - 홈 화면이 백업 전과 같음(인계 Markdown 출력도 바이트 단위로 같음)

## 8. 첫 번째 구현 작업 (다음 세션 착수용)
